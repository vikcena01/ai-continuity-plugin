Rewrote with `git filter-branch --tree-filter` (git-filter-repo was not installed) to purge a work email address from the content of 3 commits, then remapped the four commit hashes cited in claim bodies by matching subjects. Any SHA quoted in an external note, issue, or session transcript from before 2026-08-26 no longer exists — resolve them by commit SUBJECT, not hash.

Lesson 1 — filter-branch leaves the pre-rewrite history in refs/original/, so a naive grep of `git log --all -p` still finds the purged string and looks like failure. The refs must be deleted, the reflog expired, and `gc --prune=now` run before the objects are actually unreachable. Verify with `git grep <string> $(git rev-list --all)`, not by inspecting working-tree files.

Lesson 2 — a blanket string replacement edits text ABOUT the string as readily as the string itself. The q6f8 claim body quoted the address while explaining the leak; the rewrite substituted the replacement address into that sentence, so the claim ended up asserting that the NEW personal address was the one exposed in 3 commits. False, and alarming to anyone reading the published state. Fixed by hand in 1c010c3. Rule: after purging a string from history, re-read every document that DISCUSSED it, and in future describe such a value rather than quoting it.
